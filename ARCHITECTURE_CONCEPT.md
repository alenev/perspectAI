# 🏛️ Архітектура мультиагентної ai-системи командного мислення й розвитку perstectAI  

## Переваги системи
> команда з різними ролями AI-агентів (наприклад CEO, CTO, CCO, CFO) працює в сімбіозі з людиною (HUMAN-IN-THE-LOOP) в середовищі тікет-системи в Notion із використанням динамічної бази знань;
> назначення обробки тікетів як всій команді агентів так і окремому агенту (питання спеціалісту або до всій команди);
> дискуссії й мозкові штурми між ai-агентами в ході обробки завдань тікетів (планування й розвиток напрямків діяльності);
> оптимізація результатів міркувань ai-агентів для фокусі на стислій конкретиці 'без води' (більша ефективність прогресу й менші витрати);
> автоматична звітність витрат токенів (ресурсів) після обробки тікету;



## 📌 Загальний огляд системи
Дана архітектура створена для проектування, запуску та операційного управління бізнесом з інтеграції AI в українські компанії з нуля. Система побудована на принципі **Human-in-the-Loop (HITL)** — гібридної взаємодії, де чотири ШІ-агенти С-рівня (CEO, CTO, CCO, CFO) ведуть автономні дебати, а Користувач (Людина) виступає в ролі головного валідатора, стратега та операціоніста.

## 🛠️ Технологічний стек та інтеграція
* **Оркестратор:** Автономна служба на базі Node.js (`orchestrator.js`), яка здійснює безперервне фонове опитування (polling) бази Notion та координує мультиагентний рій. 
* **Запуск системи:** `node orchestrator.js`
* **Базова LLM:** Гібридна модельна сітка через OpenRouter або напряму через DeepSeek API (вибір здійснюється за допомогою змінної `LLM_PROVIDER` у `.env`):
  - При `LLM_PROVIDER=DEEPSEEK`: пряме підключення до `https://api.deepseek.com/chat/completions` (використовуються моделі `deepseek-v4-pro` для Оркестратора/CEO/CTO та `deepseek-v4-flash` для CCO/CFO).
  - При `LLM_PROVIDER=OPENROUTER`: підключення через OpenRouter (моделі `deepseek/deepseek-v4-pro` та `deepseek/deepseek-v4-flash`).
* **Операційний розділ (Notion):** Інтеграція через офіційний **Model Context Protocol (MCP)** сервер `@notionhq/notion-mcp-server`. Для гарантування працездатності додавання коментарів при багах MCP, оркестратор використовує нативний REST API клієнт.
* **Пошукова система та оптимізація:** Веб-пошук в реальному часі через MCP-сервер `google-surf-mcp`. Для економії токенів інтегровано інструменти лексичного пошуку `lexical_search` та `visit_page_lexical_search`, які дозволяють точково вилучати релевантні сегменти тексту замість читання повних сторінок.
* **Обмеження квот та токенів:** Впроваджено автоматичний токен-регламент. Якщо сумарні витрати (Input Cache miss + Output) перевищують встановлений ліміт, система переводить завдання в статус `"Token Planning"` та перепризначає на `DENIS`.

## 📂 Гібридне сховище даних та Топологія проєкту

### 1. Контур Локального Проєкту (Внутрішня логіка)
* `INSTRUCTIONS.md` — головний регламент та алгоритм сканування Notion, правила запуску дебатів, ліміти токенів та правила лаконічності (Zero-Fluff Protocol).
* `ROADMAP.md` — динамічний стратегічний трекер та довгострокова пам'ять проєкту. Моделі точково оновлюють його локально після закриття завдань.
* `.system_roles/` — профілі обмежень та ментальних фільтрів для **CEO**, **CTO**, **CCO** та **CFO**.

### 2. Контур Хмари Notion (Операційна панель для Людини)
* **База даних `TICKETS_SYSTEM` (AI-Integrator Hub):** Операційний простір для тасків.
* **База даних `KNOWLEDGE_BASE` (wiki):** Сховище констант компанії. Кожна сторінка має текстове поле `Short Summary` для швидкого лексичного пошуку агентами.

## ⚡ Механіка взаємодії (Воркфлоу)
* **Контроль доступності пошуку:** При запуску оркестратор тестує пошуковий інструмент. У разі його збою система автоматично вимикається, заздалегідь створюючи репорт-тікет для `DENIS`.
* **Фільтрація фактологічних запитів (Triage):** Прості та фактологічні запити (Tier 1) оркестратор обробляє самостійно без скликання глобального консиліуму.
* **Менеджерська роль Оркестратора:** Якщо тікет призначений конкретній ролі (CTO, CCO і т.д.), Оркестратор діє виключно як менеджер: не робить самостійного аналізу/пошуку, а одразу перенаправляє роботу відповідному спеціалісту.
* **Zero-Fluff Protocol:** Усі агенти генерують максимально стислі відповіді без мета-тексту, привітань та резюмувань.
* **Автоматичний звіт токенів:** Після завершення обробки тікета оркестратор окремим коментарем додає блок `=== SUMMARY TOKENS ===` із розрахунком фактично витрачених токенів на дебати.
* **Ініціація:** Користувач створює картку завдання в Notion (база `AI-Integrator Hub`), виставляє властивість `Assignee Role = AI` та `Status = In progress` (або статус, визначений у `.env`).
* **Активація (Фонове опитування):** Служба оркестратора постійно сканує Notion з інтервалом опитування, визначеним у `.env`.
* **Валідація (HITL):** Після завершення раундів дебатів Оркестратор пише підсумковий висновок у `Summary Box` (якщо властивість є в Notion, або додає блок тексту), переводить `Status` в `"Needs Review"`, а `Assignee Role` перемикає на `DENIS` (Людина).
