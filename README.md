# 🤖 perspectAI — Мультиагентна AI-система командного мислення й розвитку

**perspectAI** — це інтелектуальна AI-оркестраційна платформа, розроблена для проектування, запуску та операційного управління бізнесом на базі Notion та штучного інтелекту. Система реалізує гібридну взаємодію **Human-in-the-Loop (HITL)**: чотири спеціалізовані AI-агенти C-рівня ведуть автономні дебати під наглядом AI-модератора, тоді як людина виступає головним стратегом і валідатором рішень.

---

## ⚡ Ключові переваги та можливості

* **Гібридний симбіоз (Human-in-the-Loop):** Спільна робота AI-агентів і людини в інтегрованому середовищі Notion (Канбан-дошка завдань + База знань Wiki).
* **Спеціалізовані експертні ролі:** Розподіл завдань між агентами **CEO**, **CTO**, **CCO** та **CFO** відповідно до їхнього профілю та компетенцій.
* **Гнучке призначення (Triage):** Можливість адресування тікетів як окремим спеціалістам (цільовий запит), так і всій команді агентів одночасно (глобальний консиліум).
* **Програмна оркестрація:** Координація рою реалізована через Node.js сервіс із залученням сильної reasoning-моделі на посаді **MODERATOR** (менеджер контексту, аналітик відповідей та верифікатор результатів).
* **Дискусії та мозкові штурми:** Проведення дебатів між експертами для пошуку збалансованого рішення з автоматичним виявленням протиріч.
* **Протокол лаконічності (Zero-Fluff Protocol):** Оптимізація відповідей агентів для уникнення зайвого мета-тексту ("води"), що фокусує висновки на конкретиці та заощаджує ресурси.
* **Контроль бюджету та звітність:** Автоматичний розрахунок і виведення звіту про витрачені токени після кожного тікета та перехід в статус `Token Planning` у разі лімітного перевищення.
* **Уникнення колізій:** Автоматичне виявлення й завершення застарілих процесів оркестратора при повторному старті системи.

## 🙍 Типовий цикл роботи із системою (гібридний симбіоз Human-in-the-Loop)
1. Користувач в Notion в новому тікеті формує звернення в описі або в існуючому тікеті додає коментар.
2. Користувач призначає обробку тікету всім ai-агентам (AI) або окремому агенту (CEO/CTO/CCO/CFO).
3. Користувач змінює статус тікета на In Progress.
4. Оркестратор в 10-секундному інтервалі пошуку тікетів зі статусом In Progress починає обробку контексту тікету й передає контекст модератору. 
5. Модератор згідно з аналізом контексту тікету викликає (релевантних призначенню обробці тікету, окремих або всіх) агентів й направляє їм питання відносно експертності агентів.
6. Модератор отримує від агентів стислі експертні відповіді й компонує їх у свою загальну результуючу відповідь. Якщо модератор бачить суперечки між експерними висновками агентів, то він вирішує їх з відправленням, за потреби, додаткових питань агентам з метою отримання консенсусу між відповідями агентів.
7. Модератор додає в коментарі тікету звіт з висновками по результату обробки тікету із окремими експертними відповідями агентів.
8. Оркестратор оновлює `KNOWLEDGE_BASE` із внесенням туди нових знань.
9. Оркестрато оновлює локальний `ROADMAP.md` з внесенням в нього інформації по загальному прогресу.
10. Оркестратор додає в коментарях тікета підсумок витрачених токенів на обробку тікету окремо по різним моделям.

## 🏛️ Архітектура та розподіл ролей

Система розділена на два основні контури:
1. **Локальний контур (Внутрішня логіка):** Локальні файли конфігурацій, профілі агентів та локальний `ROADMAP.md` для збереження стратегічного фокусу.
2. **Хмарний контур (Notion):** База даних завдань `TICKETS_SYSTEM` та база знань `KNOWLEDGE_BASE`.

### Рольова модель:
* **Оркестратор (`orchestrator.js`):** Програмний контролер, який сканує Notion, координує запити, контролює доступність інструментів пошуку та викликає агентів.
* **Експерти (CEO, CTO, CCO, CFO):** Відповідають на профільні запити, проводять пошук в мережі та аналізують документацію на базі легких, швидких й дешевих моделей (`flash`).
* **Модератор (MODERATOR):** Валідує відповіді експертів за допомогою глибоких reasoning моделей (`pro`), формує кінцеве резюме та повертає тікет користувачу.
* **Користувач:** Кінцевий отримувач рішень, валідатор та стратег.

## 🛠️ Технологічний стек

* **Runtime:** Node.js (ES Modules)
* **LLM інтеграція:** Пряме підключення до **DeepSeek API** або через провайдер **OpenRouter** (визначається конфігурацією `.env`).
* **Notion інтеграція:** Офіційний SDK `@notionhq/client` + підтримка **Model Context Protocol (MCP)**.
* **Пошукова система:** Веб-пошук в реальному часі через `google-surf-mcp` (з вбудованими інструментами точкового лексичного пошуку `lexical_search` та `visit_page_lexical_search` для економії вхідних токенів).

## ⚙️ Встановлення та Налаштування

### 1. Налаштування Notion

Для роботи системи потрібна інтеграція з Notion та дві бази даних. Виконайте наступні кроки для їх налаштування:

#### А. Отримання токену інтеграції
1. Перейдіть на сторінку керування токенами [Notion Developers - Tokens](https://app.notion.com/developers/tokens).
2. Створіть нову інтеграцію (натиснувши кнопку **Create new token** або схожу), вкажіть назву та виберіть Workspace, у якому ви працюєте.
3. Переконайтеся, що інтеграції надано права на читання, запис та додавання коментарів.
4. Скопіюйте створений **Internal Integration Token** (це значення вказується як `NOTION_API_KEY` у файлі `.env`).

#### Б. Створення батьківської сторінки та баз даних
У інтерфейсі Notion (у вашому Workspace / Personal Home) виконайте такі кроки:

1. **Створіть батьківську сторінку:** натисніть **Add a page** (+) та назвіть її (наприклад, `AI-team page`).
2. **Створіть дві вкладені бази даних всередині цієї сторінки:**
   * **База тікетів:** рекомендується використовувати формат Канбан-дошки. Назвіть її, наприклад **`AI-team tickets`**.
   * Обов'язкові властивості (Properties):
     * **`Name`** (тип: `Title`) — назва завдання/тікета.
     * **`Status`** (тип: `Status`) — життєвий цикл тікета. Обов'язково додайте статуси: `Not started`, `In progress`, `Needs Review`, `Token Planning`, `Done`.
     * **`Assignee Role`** (тип: `Select`) — роль виконавця. Додайте опції: `AI` (для глобального консиліуму), `CEO`, `CTO`, `CCO`, `CFO` та ім'я вашого користувача (наприклад, `DENIS`).

   * **База знань Wiki:** створіть другу базу даних та назвіть її **`wiki`**.
     * Обов'язкові властивості (Properties):
       * **`Name`** (тип: `Title`) — назва статті/правила.
       * **`Short Summary`** (тип: `Text` / `Rich Text`) — короткий сухий опис вмісту. AI-агенти використовують це поле для швидкого лексичного пошуку, щоб не завантажувати довгі тексти та економити вхідні токени.

#### В. Перевірка доступу до сторінки
Якщо створена інтеграція належить до того ж самого Workspace, оркестратор зазвичай може автоматично знайти батьківську сторінку `AI-team page` та її бази даних за їх назвами. 


### 2. Клонування та встановлення залежностей
```bash
npm install
```

### 3. Налаштування файлу `.env`
Створіть файл `.env` у кореневій директорії проєкту та вкажіть конфігурацію:

```env
LLM_PROVIDER=DEEPSEEK
# Логування в orchestrator.log деталізації активності оркестратора
DEBUG=false
# скорочений формат підсумків використання токеів обробки тікету 
TOKENS_SUMMARY_SHORT=true

# Ключі доступу
DEEPSEEK_API_KEY=
NOTION_API_KEY=

# інтервал моніторінгу появи у тікету статус-тригера обробки тикету оркестратором
POLLING_INTERVAL_MS=10000
# статус-тригер обробки тикету оркестратором
ACTIVE_STATUSES="In progress"
# ліміт вхідних токенів при обробці тікету
TICKET_PROCESS_TOKENS_LIMIT=50000

DEEPSEEK_ROLE_MODERATOR_MODEL=deepseek-v4-pro
DEEPSEEK_ROLE_ORCHESTRATOR_MODEL=deepseek-v4-flash
DEEPSEEK_ROLE_CEO_MODEL=deepseek-v4-flash
DEEPSEEK_ROLE_CTO_MODEL=deepseek-v4-flash
DEEPSEEK_ROLE_CCO_MODEL=deepseek-v4-flash
DEEPSEEK_ROLE_CFO_MODEL=deepseek-v4-flash
```

## 🚀 Запуск та Використання

### Стандартний запуск
Запуск системи оркестрації у фоновому режимі для безперервного моніторингу Notion:
```bash
npm start
```
*або безпосередньо:*
```bash
node orchestrator.js
```

### Відлагодження конкретного тікета (Debug Mode)
Для тестування роботи оркестратора на конкретному завданні без зміни його статусу в Notion використовуйте:
```bash
node orchestrator.js --debug-ticket "ID_або_назва_тікета"
```
Ця команда збереже повні дані тікета у файл `debug_ticket.json` для подальшого аналізу.

### Перевірка конфігурації
```bash
npm run check
```
